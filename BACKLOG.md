# Беклог wasmhost

Фазовий план. Порядок фаз — від дешевого й потрібного іншим пунктам до дорогого й залежного від рушіїв.
Позначки: `[x]` зроблено, `[ ]` не зроблено, `[~]` частково. Розмір: **S** (до дня), **M** (кілька днів),
**L** (тиждень і більше). «Бекенди» — де це реально можна зробити; решта чесно каже `supports(...) == False`.

Стан на `main` (комміт `260f11c`) звірено з кодом і `git log`. Що лежить поза цим репозиторієм, тут не перевірялося
і позначено «не перевірено»; єдиний виняток: `tiny-bclibc-wasm` перевірено й він працює (це підтвердив власник).

## Правило: селф-тест іде разом із функцією

Рантайми вже перевіряє CI: весь набір `pytest` проганяється окремо на кожному бекенді (`wasmtime`, `node`, `wasm3`,
`jsc` і `jscontext` на macOS, WebKitGTK `jsc` і `gi-jsc` з JIT і без JIT, як на iOS), плюс крок «Examples».
Цього не замінює селф-тест (`python -m wasmhost selftest`, `wasmhost.selftest()`): він запускається **на пристрої** (iPhone,
Pythonista), де CI не буває. Він має відображати те, що бібліотека вміє зараз, тож його оновлюють **у тому ж PR**, що
й саму функцію:

- Нова або змінена можливість отримує крок у `_selftest.py` (за зразком `_globals_on_their_own`, `_exceptions`).
  Крок, що залежить від рушія, спершу питає `backend.supports(...)` і, якщо ні, чесно пише «не підтримується», а не
  падає.
- Модуль для кроку будується в `tests/wasm_builder.py`, а `tests/test_selftest.py` перевіряє, що байти в
  `_selftest.py` збігаються з білдером (так уже зроблено для `MODULE`, `CALLBACKS`, `EXCEPTIONS_*`).
- Змінена поведінка (наприклад, `Table.get` стає викликаною функцією) змінює відповідний крок, а не додає
  новий поруч.
- `test_selftest_passes_on_every_backend` проганяє селф-тест на кожному бекенді в CI; зелений прогін на пристрої
  фіксується в README так само, як зроблено для iPhone 16 (PR #8).
- Тести в CI перевіряють бібліотеку, селф-тест перевіряє її на пристрої: одне не замінює іншого.
- Видалена функція — видалений крок.

## Прийняті рішення про API

Принцип власника: фасад близький до JS WebAssembly API (JavaScriptCore), це альфа, тож зламати старе заради
чистого API можна.

- `type()` на `Function`, `Memory`, `Table`, `Global` як метод, з іменами з JS type reflection; `Global.type`
  перестав бути рядком (зроблено).
- Помилка виконання лишається `Trap` (підклас `RuntimeError`), а не `RuntimeError`: ім'я вбудоване в Python і
  затьмарювалось би, а «trap» це термін самої специфікації. README уже каже, що це `WebAssembly.RuntimeError`.
- Числа лишаються `int`/`float` (`i64` ↔ Python `int` відповідає `BigInt`); `ctypes`-типи розглянути пізніше,
  лише якщо захочемо змінити поведінку.
- Пам'ять без копіювання на пізніше (B-301).
- Async: `async def compile/instantiate` плюс `instantiate_sync`, без гонок (B-304).
- лише `Function` і `FuncType` (`FuncRef` прибирається): `Function.signature` необов'язковий, `type()` розв'язує
  його ліниво, виклик без підпису теж (B-201); власні типи значень `i32`/`i64`/`f32`/`f64` як підклас `str` (B-205).

## Фаза 2. Таблиці й посилання (M–L)

- [ ] **B-201** `Table.get` повертає викликану `Function`; `FuncRef` зникає. У JS цього питання нема: `table.get(i)`
      дає звичайну викликану функцію, та сама, що й експорт (`table.get(0) === exports.add`), бо рушій знає тип
      зсередини (перевірено на JSC 2.52.6 і V8). JS-API сигнатури нам не віддає (`WebAssembly.Function` є лише у
      V8 за прапорцем), тож відновлює її Python.
      **Погоджено (власник):**
      - **лише два типи: `Function` і `FuncType`.** `Function` це все, що викликається: експорт і запис таблиці;
        `FuncType` це єдиний опис підпису (`parameters`, `results`) у дескрипторах, `type()` і `signature`;
        `FuncRef` прибирається з публічного API (це альфа, ламати можна);
      - поле **`Function.signature`**: `FuncType` або `None` («не задано»); читання нічого не розв'язує й не
        кличе рушій; присвоєння атомарне цілим значенням: `f.signature = FuncType((i32, i32), (i32,))`; нема
        половинчастого стану; експорт має `signature` з моменту створення (з дескриптора);
      - **`Function.type()` розв'язує ліниво й повертає `FuncType`**: якщо `signature` є, повертає його, якщо ні,
        шукає, кладе в `signature` і повертає, а якщо не вдалося, кидає `ValueError` («сигнатуру не знайдено,
        задайте `signature`»); де бекенд не має доступу до таблиць, `NotImplementedError`. Окремого
        `resolve_*`, `cast`, `.annotated` і параметра `resolve=` **немає**. Невдачу не кешує;
      - виклик `f(...)` без `signature` ліниво розв'язує її через `type()`, один раз; виняток іде без змін;
      - присвоєне вручну ніколи не перезаписується розв'язанням;
      - `f.parameters`/`f.results` (і старі `Function.params`) лишаються лише як читання з `signature`;
      - помилки не ковтаємо й не обгортаємо;
      - `table.get` кешує `Function` за (таблиця, функція): `table.get(0) is table.get(0)`, як у JS.
      **Де сигнатура розв'язується сама:** wasmtime (рушій дає типи), експорти, записи, які поклав хост через
      `table.set`, функції з активних сегментів `elem` (розбір у Python); wasm3 не має доступу до таблиць.
      `f.length` у JS-рушіях дає кількість параметрів: дешева перевірка на узгодженість.
      **Хибний `signature`:** wasmtime перевіряє і кидає помилку, JS-рушії ні (`Number` замість `BigInt` дасть
      помилку рушія, `i32` замість `f64` мовчки хибний результат). Відповідальність викликача, іде в README.
      **Рівність і хеш (погоджено):** дві `Function` рівні, якщо це **та сама функція в рушії**; `signature` у
      `__eq__` і `__hash__` **не входить** (він може з'явитись пізніше, хеш мусить бути стабільним). Один об'єкт
      на одну функцію (кеш, нижче), тож `table.get(0) is table.get(0)` і `table.get(0) is exports.add`; а якщо кеш
      колись скине об'єкт, нова обгортка тієї ж функції дає рівне значення й той самий хеш. Підписи порівнюються
      явно: `a.signature == b.signature` (`None` проти `FuncType` дає `False`, це не помилка) або `a.type() ==
      b.type()`, який за потреби розв'язує.
      **Не суперечити відомому (погоджено, за умови, що це не ламає виклик):** якщо підпис відомий напевно (з
      дескриптора модуля, від рушія, з сегмента `elem`, від `table.set`), присвоїти **інший** вручну не можна:
      `ValueError` одразу при присвоєнні, а не при виклику («ця функція має підпис X»). Присвоїти **такий самий**
      можна завжди. Заповнити порожнє можна, суперечити відомому ні (об'єкт один, хибна анотація зламала б усі
      посилання на нього).
      **Один код на різних бекендах (погоджено):** користувач пише однаково, різниться лише те, звідки береться
      підпис. Експорти: підпис з бінарника на **всіх** бекендах. Записи таблиці: wasmtime дає тип рушій
      (`Func.type(store)`); JS-рушії беруть з розбору `elem`, із записів `table.set` і з експортів; лишається
      рідкісний випадок (модуль сам записав функцію в таблицю під час роботи), де на JS-рушії буде зрозумілий
      `ValueError`. **Переносний рецепт:** `f.signature = FuncType(...)` працює однаково скрізь (на wasmtime, якщо
      збігається з відомим). `supports("table.signatures")` каже, чи бекенд сам розв'язує підписи записів таблиці.
      wasm3 не має таблиць: там `NotImplementedError`.
      **Застереження для `elem`:** підпис із сегмента `elem` дійсний, доки запис не перезаписано; перезапис, зроблений
      кодом модуля, ми побачити не можемо. Тому на JS-рушіях це **підказка з перевіркою**: кількість параметрів
      порівнюється з `f.length` самої функції в рушії, а при розбіжності підпис не береться (`ValueError`).
      **Кеш (погоджено):** `Function` кешується за ключем функції в рушії; кеш на слабких посиланнях, щоб нічого не
      утримувати довше потрібного. wasmtime-py віддає **нову** Python-обгортку `Func` на кожен `table.get`
      (`exports[...]` кешує сам); ключ обох однаковий: `(store_id, внутрішній індекс)` із `Func._func`. Ми шукаємо
      за ним у своєму кеші, віддаємо наявний `Function`, а нову обгортку викидаємо. Це **приватні** поля
      wasmtime-py: потрібен тест, що ловить зміну. Для JS-рушіїв ключ це `===` у реєстрі обв'язки (один об'єкт,
      один ключ).
      **Один шлях виклику (погоджено, шлях 1):** зараз `Function.__call__` і `Batch` (`CallStep(…,
      function.name, …)`) звертаються до бекенда за парою (екземпляр, ім'я експорту), а запис таблиці має лише
      `handle`. Усе переходить на виклик за `handle` (`call_ref`): wasmtime прямий виклик `Func`, JS-рушії за
      ключем у реєстрі обв'язки (з `BigInt` для `i64`); `Batch` теж. На wasm3 handle це функція pywasm3 для
      експорту (виклик експортів лишається, таблиць нема). Для користувача синтаксис `instance.exports.add(2, 3)`
      **не змінюється в жодному разі**; для JS це навіть ближче: `exports.add` там уже сама функція, а не пошук за
      ім'ям на кожен виклик.
      Селф-тест: крок про `Function` з відомою й невідомою сигнатурою, `type()` і розв'язання; звичайні тести.
- [ ] **B-202** `Table(kind, initial, maximum, init)`: початкове значення.

## Фаза 3. Швидкість і пам'ять (M–L)

- [ ] **B-301** (відкладено за планом) Пам'ять без копіювання на нативних бекендах (wasmtime, wasm3): `memoryview` над буфером рушія,
      із чесним правилом: уявлення стає недійсним після `grow`. На JS-бекендах лишається копія.
- [ ] **B-302** Бенчмарк: `examples/coremark.py` плюс вимір передачі великих буферів (кадр, мегабайти) до й після.
- [ ] **B-303** Пакетні `read/write` для багатьох ділянок за один виклик (менше переходів рушій↔Python).
- [ ] **B-304** Асинхронні `compile`/`instantiate`, як у JS, де `WebAssembly.compile/instantiate` повертають проміс.
      Пропозиція (на обговорення): `async def compile(...)` і `async def instantiate(...)` на `asyncio`, а синхронні
      `Module(...)`/`Instance(...)` лишаються (це JS-конструктори) і ще `instantiate_sync` для нинішнього
      синхронного `instantiate` (його зараз можна перейменувати: це зміна, що ламає). Робота у потоці
      (`asyncio.to_thread`) лише на бекендах, де це безпечно (wasmtime: компіляція не торкається сховища; Node:
      запит і так іде в окремий процес), а на `jscontext`/`jsc`, прив'язаних до потоку, виконується на місці з
      `await asyncio.sleep(0)` до й після. Позначити через `supports("threads")`. **Вимога власника: без гонок.**
      Жодних одночасних викликів у один бекенд: на кожен бекенд один замок (або черга), потік виконує лише одне
      завдання за раз, а результат повертається в цикл подій через `loop.call_soon_threadsafe`. Тест на конкурентні
      `gather(instantiate(...), instantiate(...))`. Тести через `asyncio.run`, крок у
      селф-тесті.

Селф-тест: крок «пам'ять без копіювання» (уявлення недійсне після `grow`) і крок для асинхронного `compile`;
рядок «call cost» доповнити вимірюванням передачі буфера.

Готово, коли: передача буфера в мегабайти не копіюється на wasmtime і wasm3, а бенчмарк це показує.

- [ ] **B-403** Тести «модуль зі нескінченним циклом» на кожному бекенді, що це вміє.

Ризики: JSC без переривання, тож на iOS це не гарантується; потрібна окрема нотатка про те, чого пісочниця не

Готово, коли: нескінченний цикл переривається з `Trap`-подібною помилкою там, де рушій це підтримує.

## Фаза 5. WASI (відкладено за рішенням власника, L)

Рішення: «WASI на пізніше». Нічого не чіпати без команди. Підготовчий матеріал уже є на гілці `examples/zigcc`:
клас `Wasi` у `examples/coreutils.py` (понад 40 викликів, обидва знімки `wasi_snapshot_preview1` і `wasi_unstable`,
файли у справжній папці, stdio, аргументи, годинник, `sleep`), тести на wasmtime і node.

- [ ] **B-501** Вирішити форму: необов'язковий модуль `wasmhost.wasi` чи окремий пакет `wasmhost-wasi`.
- [ ] **B-502** Перенести `Wasi` з прикладу, з API на кшталт `Wasi(args=…, preopens={"/": dir}, stdin=…, stdout=…)`.
- [ ] **B-503** Пісочниця через `openat` із `dir_fd`, щоб прибрати розрив між перевіркою шляху й відкриттям
      (зараз `resolve()` перевіряє, потім `os.open`).
- [ ] **B-504** Кілька preopen-папок і режим «лише читання».
- [ ] **B-505** Тести на всіх бекендах; `wasm3` не бере збірки Rust (multi-value, reference types), це в `supports`.
- [ ] **B-506** Команда запуску модуля за зразком `wasmtime myapp.wasm -- arg1 arg2 --verbose`. Граматика:
      `wasmhost [ОПЦІЇ ХОСТА] myapp.wasm [-- АРГУМЕНТИ ПРОГРАМИ]`: опції до модуля належать хосту (`--backend`,
      `--dir ХОСТ::ГІСТЬ`, `--env K=V`), усе після модуля (і після `--`) без розбору йде програмі через

- [ ] **B-507** Точка входу `wasmhost`: `[project.scripts] wasmhost = "wasmhost._cli:main"` в `pyproject.toml`, щоб
      писати `wasmhost myapp.wasm` і `wasmhost selftest`, а не `python -m wasmhost`. Зараз такої команди нема.
      Перевірити `uv lock --check` і колеса.
- [ ] **B-508** Запуск модуля без WASI (як наші `fib` і `sum`): в нього нема `_start` і аргументів, тому окрема

Селф-тест: крок WASI (запустити крихітну WASI-програму: `fd_write` у stdout, `args`, файл у тимчасовій папці).

Поза обсягом: сокети, потоки, інтерактивний stdin, WASI preview2.

## Ідеї, не заплановані

- **Числа як типи `ctypes`.** Нині `i32` і `i64` це `int`, а `f32` і `f64` це `float` (`i64` ↔ Python `int` відповідає
  JS `BigInt`). Альтернатива: типи в дусі `ctypes` (`c_int32`, `c_int64`, `c_float`) для аргументів і результатів.
  Розглядати пізніше, лише якщо захочемо змінити поточну поведінку.
- **Пам'ять через `ctypes`.** Вікно на пам'ять рушія (`memoryview`/`ctypes`-масив) на нативних бекендах: пов'язано з
  B-301.

## Відомі проблеми прикладів (не API)

- `examples/wasm/lua.wasm` зібрано без `longjmp`: будь-яка помилка скрипта (синтаксис, `error()`, `pcall`) вбиває
  інтерпретатор. Лікування — інша збірка Lua.
- `coreutils.wasm` не запускається на `wasm3` (multi-value, reference types, bulk memory).
- Чи бере JavaScriptCore на твоєму iOS решту можливостей `coreutils.wasm`, не перевірено на пристрої.
- `coreutils.wasm` важить 10,8 МБ (див. B-004).
