# Беклог wasmhost

Фазовий план. Порядок фаз — від дешевого й потрібного іншим пунктам до дорогого й залежного від рушіїв.
Позначки: `[x]` зроблено, `[ ]` не зроблено, `[~]` частково. Розмір: **S** (до дня), **M** (кілька днів),
**L** (тиждень і більше). «Бекенди» — де це реально можна зробити; решта чесно каже `supports(...) == False`.

Стан на `main` (комміт `260f11c`) звірено з кодом і `git log`. Що лежить поза цим репозиторієм (tiny-bclibc-wasm,
гілка `jsc-runner`, Android), тут не перевірялося і позначено «не перевірено».

## Фаза 1. Інтроспекція модуля (S–M, чистий Python у `_binary.py`)

- [ ] **B-101** Ліміти в `ImportDescriptor` і `ExportDescriptor`: для пам'яті `min`, `max`, прапорці `shared` і

- [ ] **B-102** `mutable` в `ExportDescriptor` для глобалів (в імпортах уже є).
- [ ] **B-103** `type()` для `Memory`, `Table`, `Global`, `Function`: дескриптор із лімітами (за зразком

- [ ] **B-104** Допоміжний конструктор, що створює `Memory`/`Table`/`Global` за дескриптором імпорту, щоб хост не

Тести: `tests/wasm_builder.py` будує модулі з різними лімітами. Бекенди: всі (розбір бінарника, без рушія).

Готово, коли: для довільного модуля можна автоматично зібрати імпорт-об'єкт із пам'яті й таблиць, що він просить.

## Фаза 2. Таблиці й посилання (M–L)

- [ ] **B-201** `Table.get` повертає викликану `Function`, а не опаковий `FuncRef`. Потрібна сигнатура: wasmtime дає
      її сам, JS-рушії ні, тому обхід через розбір секцій типів і функцій у бінарнику (спирається на B-101).
- [ ] **B-202** `Table(kind, initial, maximum, init)`: початкове значення.
- [ ] **B-203** `externref` і `funcref` як значення глобалів і таблиць (зараз лише числа) і `Table("externref", …)`.
      Рішення з дизайну: як тримати Python-об'єкти на боці рушія (реєстр з ручками, звільнення).
- [ ] **B-204** Multi-value у `Batch`: кортеж результатів у пакеті (зараз README каже «не підтримується»).

Бекенди: wasmtime (повністю), wasm3 (частково), JS-рушії (через обгортки); те, чого нема, позначається
`supports("table.externref")` тощо. Ризик: `externref` у JSC/Node потребує окремого шляху.

Готово, коли: `instance.exports.table.get(0)(1, 2)` працює там, де рушій дозволяє, а де ні — зрозуміла помилка.

## Фаза 3. Швидкість і пам'ять (M–L)

- [ ] **B-301** Пам'ять без копіювання на нативних бекендах (wasmtime, wasm3): `memoryview` над буфером рушія,
      із чесним правилом: уявлення стає недійсним після `grow`. На JS-бекендах лишається копія.
- [ ] **B-302** Бенчмарк: `examples/coremark.py` плюс вимір передачі великих буферів (кадр, мегабайти) до й після.
- [ ] **B-303** Пакетні `read/write` для багатьох ділянок за один виклик (менше переходів рушій↔Python).
- [ ] **B-304** Асинхронні `compile`/`instantiate` як тонка обгортка над потоками (для довгої компіляції великих
      модулів на телефоні).

Готово, коли: передача буфера в мегабайти не копіюється на wasmtime і wasm3, а бенчмарк це показує.

## Фаза 4. Обмеження для ненадійного коду (L)

- [ ] **B-401** Ліміт пам'яті: використовувати `maximum` із B-101 і ліміти рушія; перевірка, що `grow` понад ліміт
      повертає -1, а не кладе процес.
- [ ] **B-402** Таймаут або паливо виконання: `fuel`/`epoch` на wasmtime, `gas`-аналог на wasm3, переривання на Node
      (окремий процес). `supports("timeout")` буде `False` на JSC: це чесно написати в README.
- [ ] **B-403** Тести «модуль зі нескінченним циклом» на кожному бекенді, що це вміє.

Ризики: JSC без переривання, тож на iOS це не гарантується; потрібна окрема нотатка про те, чого пісочниця не
обіцяє.

Готово, коли: нескінченний цикл переривається з `Trap`-подібною помилкою там, де рушій це підтримує.

## Фаза 5. WASI (відкладено за рішенням власника, L)

Рішення: «WASI на пізніше». Нічого не чіпати без команди. Підготовчий матеріал уже є на гілці `examples/zigcc`:
клас `Wasi` у `examples/coreutils.py` (понад 40 викликів, обидва знімки `wasi_snapshot_preview1` і `wasi_unstable`,
файли у справжній папці, stdio, аргументи, годинник, `sleep`), тести на wasmtime і node.

- [ ] **B-501** Вирішити форму: необов'язковий модуль `wasmhost.wasi` чи окремий пакет `wasmhost-wasi`.
- [ ] **B-502** Перенести `Wasi` з прикладу, з API на кшталт `Wasi(args=…, preopens={"/": dir}, stdin=…, stdout=…)`.
- [ ] **B-503** Пісочниця через `openat` із `dir_fd`, щоб прибрати розрив між перевіркою шляху й відкриттям
      (зараз `resolve()` перевіряє, потім `os.open`).
- [ ] **B-504** Кілька preopen-папок і режим «лише читання».
- [ ] **B-505** Тести на всіх бекендах; `wasm3` не бере збірки Rust (multi-value, reference types), це в `supports`.

Поза обсягом: сокети, потоки, інтерактивний stdin, WASI preview2.

## Відомі проблеми прикладів (не API)

- `examples/wasm/lua.wasm` зібрано без `longjmp`: будь-яка помилка скрипта (синтаксис, `error()`, `pcall`) вбиває
  інтерпретатор. Лікування — інша збірка Lua.
- `coreutils.wasm` не запускається на `wasm3` (multi-value, reference types, bulk memory).
- Чи бере JavaScriptCore на твоєму iOS решту можливостей `coreutils.wasm`, не перевірено на пристрої.
- `coreutils.wasm` важить 10,8 МБ (див. B-004).

## Загальне означення «готово»

Код, тести в `tests/` на всіх бекендах, що можуть це зробити (решта пропускається з причиною), `pre-commit`
зелений (pyright, ruff, pytest), зміна відображена в README і в «Not yet», `supports(...)` чесно описує, де це не
працює.
